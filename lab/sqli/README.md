# SQLi 复测靶场（最小单例）

一个应用，七种"修复"形态，八张工单。目的是让你在一屏之内看清一件事：

> **同一个漏洞，可以有七种"看起来都修了"的状态，而它们的技术实质完全不同。**

这是「漏洞复测」这个选题全部知识密度的来源，也是第 5.2 节「区分实际修复与表层变更」的实物样本。

---

## 快速开始

```bash
cd lab/sqli
./run_local.sh up                    # 启动 7 个变体 + 1 个边缘网关（端口 8000-8007）
python3 ../../tools/retest_demo.py   # 取数 → 信号 → 知识库判定 → 证据链
python3 ../../tools/ablate.py        # 消融实验：证明知识库真的在起作用
./run_local.sh down                  # 停止
```

本地模式零依赖（Python 标准库 + PyYAML）。也可以用 Docker：

```bash
docker compose up -d --build
python3 ../../tools/retest_demo.py
docker compose down
```

> 两种模式都占用 8000-8007，别同时开。8008 故意不启动，它代表"网络不可达"那一例。

## 八张工单

| 工单 | 变体 | 真实状态 | 期望判定 | 验证目标 |
|---|---|---|---|---|
| SQLI-001 | `v0_vulnerable` | 完全没改 | `UNFIXED` / `no_fix` | 对照组：工单说"已修复" |
| SQLI-002 | `v1_truefix` | 三入口参数化 | `FIXED` / `root_cause` | 根因修复：变体应全灭 |
| SQLI-003 | `v2_version_only` | 只改了版本号 | `UNFIXED` / `version_only` | **版本号是声明，不是证据** |
| SQLI-004 | `v3_waf_only` | 只在网关拦截 | `MITIGATED_NOT_FIXED` / `edge_virtual_patch` | **虚拟补丁不是修复** |
| SQLI-005 | `v4_blacklist` | 关键词黑名单 | `UNFIXED` / `bypassable_filter` | **假净化**：原 PoC 被拦，变体绕过 |
| SQLI-006 | `v5_partial` | 只修了 `/api/user` | `PARTIAL` / `single_point` | **单点修复**：兄弟入口还通着 |
| SQLI-007 | `v6_broken` | 活着但取不到数 | `UNVERIFIABLE` / `baseline_broken` | **所有 payload 都失败 ≠ 已修复** |
| SQLI-008 | 端口无人监听 | 网络不可达 | `UNVERIFIABLE` / `unreachable` | **打不通 ≠ 修好了** |

---

## 三个关键教学点

### 1. 原始 PoC 被拦，不等于洞被修了

最容易被骗的是 SQLI-005。原始 PoC 是 union 注入（带引号和 `UNION SELECT`），黑名单把它们全拦了，回 400。**只重放原始 PoC 会判"已修复"。**

但这个注入点是**数字型**的，根本不需要引号：`id=1 OR 1=1` 直接返回 3 行。

所以复测的判据不是"payload 还通不通"，而是"**通道还在不在，控制是否不可绕过**"。

### 2. 打不通有很多种解释，得排除掉其余的

`UNVERIFIABLE` 至少有两个来源，必须分开：

- **SQLI-007**：进程活着，但连基线查询都拿不到数据 → 攻击全失败是假象
- **SQLI-008**：网络根本不通

两者都判"无法验证"，但原因不同、报告写法不同。**"打不通"绝不能等同于"修好了"**——这是模型最容易犯的错，所以它由代码做硬闸门，不靠提示词。

### 3. 「未修复」是阳性证据，「已修复」是阴性证明

判 `UNFIXED` 只需要一条可利用的响应；判 `FIXED` 需要五条否定同时成立（基线正常、主入口全灭、兄弟入口全灭、源站全灭、变体全灭）。

因此 `FIXED` 的置信度只标 `medium`，并要求人工抽检。**在复测里，"说已修复"的成本必须高于"说未修复"。** 这是刻意的取舍，写在 `R08_FIXED.note` 里。

## 分层结构

```
        取数层              信号层              判定层              知识库
   agent/collect.py  →  agent/signals.py  →  agent/judge.py  ←  knowledge/*.yaml
   发请求 / 存证据       证据 → 布尔量        规则求值 / 证据链      可执行判据
```

**判定层不含任何业务判据。** 所有判据都在 YAML 里，由 `judge.py` 逐条求值。想改判定逻辑，改 YAML，不改代码。

每条证据都带响应体哈希，报告里的"我打过这个请求"可自证。

## 知识库

`knowledge/false-fix-patterns.yaml` 定义 8 条规则，按优先级求值：

| 优先级 | 规则 | 结论 |
|---|---|---|
| 10 | `R01_UNREACHABLE` | 网络不可达 → 无法验证 |
| 20 | `R02_BASELINE_BROKEN` | 基线异常 → 无法验证 |
| 30 | `R03_EDGE_VIRTUAL_PATCH` | 仅边界拦截 → 仅缓解 |
| 40 | `R04_SINGLE_POINT` | 兄弟入口未修 → 部分修复 |
| 50 | `R05_BYPASSABLE_FILTER` | 原 PoC 失效但变体有效 → 未修复 |
| 60 | `R06_VERSION_ONLY` | 版本变了但可利用 → 未修复 |
| 70 | `R07_UNFIXED` | 主入口可利用 → 未修复 |
| 80 | `R08_FIXED` | 五条否定同时成立 → 已修复 |

**顺序本身是知识**：更具体的证据必须压过更一般的证据。例如"公网被拦但源站可直连"必须先于"主入口不可利用"判定，否则会误判为部分修复。

每条规则都带：`evidence_required`、`failure_modes`（失效与误判经验）、`not_evidence`（哪些字段不可作为判据及原因）。

## 消融实验

`python3 tools/ablate.py` 实测结果：

| 配置 | 裁决 | 模式 | 完全一致 |
|---|---|---|---|
| 完整知识库 | **8/8** | **8/8** | **8/8** |
| 无知识库（仅重放 PoC） | 5/8 | 3/8 | 3/8 |

逐条移除（严格模式）：8 条规则每一条被去掉后，输出都会变化。

规则命中统计：8 条规则各命中 1 次，无冗余规则。

> 消融实验的意义：**移除知识后输出必须变差**。变差多少，就是这份知识值多少。

## 已知局限

1. **只有一类漏洞**。目前仅覆盖数字型 SQL 注入。要支撑 10 分钟知识问答，至少还需 XSS、路径穿越、命令注入、越权四类。
2. **变异矩阵是手写的**，不是按漏洞类型生成的。真正的知识层要能说清"这类洞有哪些等价变形"。
3. **阈值是零噪声下标定的**。靶场响应是确定性 JSON，噪声为 0，因此 `min_row_delta=1` 只能证明流程可用。生产环境必须重测（方法写在 `thresholds.provenance`）。
4. **边缘识别是启发式的**（403 + HTML）。真实 WAF 可能返回 200 的拦截页或直接 RESET 连接。
5. **直连源站依赖实验环境可控**。生产复测必须先授权，否则是越权测试。
6. **判定层没有模型参与**。LLM 的位置在下一步：解释证据、处理信号冲突、决定升级人工。

## 实施中踩到的坑

### 坑一：网关忘记 URL 解码

**现象**：SQLI-004 判定错误，网关没拦住任何 payload，`0 UNION SELECT` 被原样转发给后端。

**定位**：探针用 `urlencode`，空格变成 `+`、`=` 变成 `%3D`；而规则匹配的是**编码后**的原始 query string，正则全部落空。用 `curl` 发编码后的 URL 复现，确认 403 变 500。

**修复**：匹配前先 `unquote_plus`。

**反思**：这个 bug 恰好就是真实世界最常见的 WAF 绕过之一——**网关忘记规范化就做字符串匹配**。我无意中写出了一个有真实缺陷的 WAF，而它暴露的正是复测要识别的绕过手法。

### 坑二：Docker 里全部判定失败（1/7）

**现象**：本地 7/7，`docker compose up` 后 1/7，所有变体都像"不可达"。

**定位**：容器日志显示 `listening on 127.0.0.1:8000`。应用绑 loopback，而 Docker 端口映射转发到**容器 IP**，落不到 loopback 上。

**修复**：绑定地址改为可配置，容器内用 `BIND=0.0.0.0`。

**反思**：本地能跑、上云就挂，是最典型的环境差异类问题。同类还有：容器内路径不可写、compose 网络里 `localhost` 指向容器自己、时区导致时间判据漂移。

### 坑三：消融实验出现假阴性

**现象**：第一版消融显示 R01、R07、R08 三条规则"移除后输出完全不变"，按 5.2 的自检口径它们该被删除。

**定位**：不是规则冗余，而是**测量方法有问题**。无规则命中时会退化到"仅重放 PoC"的朴素 fallback，而它恰好对这三例给出了相同答案，把规则的贡献掩盖了。

**修复**：加入严格模式（无规则覆盖即判 `UNVERIFIABLE`），逐条移除时用它隔离边际贡献；同时增加"规则命中统计"作为第二条证据——每条规则都实际命中过，确认被消费。

**反思**：这是本次实施里最有价值的一个坑。**消融实验本身也会骗人**：如果对照组和实验组碰巧给出相同答案，"无变化"会被误读为"该知识无用"。评估方法本身需要被验证。
