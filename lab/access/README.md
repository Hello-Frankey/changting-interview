# 越权复测靶场

三类漏洞里，这一类最贴近业务开发，也最难自动化——**因为它的响应是"正常"的**。

> SQLi 的响应里有异常（报错、行数变化）。
> XSS 的响应里有痕迹（payload 原样反射）。
> **越权的响应什么都没有：200、结构合法、数据真实。**
> 单看一个请求永远发现不了，必须做跨主体对照。

## 探针形态变了

前两类的探针是「单请求自带 payload」，越权不是。它必须是**两阶段**的：

```
阶段一（受害者视角）                   阶段二（攻击者视角）
bob 登录                                alice 登录
GET /api/orders → 拿到自己的订单 oid    GET /api/orders/{bob_oid}
                                       → 200 且返回 bob 的数据？→ 越权成立
```

**关键点：资源标识必须从受害者自己的会话里拿。** 这正是 ACC-004 想说明的——
UUID 之所以不是授权，是因为攻击者可以通过分享链接、导出文件、日志拿到它，
而本探针拿它的方式和真实攻击者完全一样。

## 七个变体

| 用例 | 变体 | "修复"方式 | 期望判定 | 验证目标 |
|---|---|---|---|---|
| ACC-001 | `a0_vulnerable` | 只校验登录 | `UNFIXED` / `no_fix` | 对照组 |
| ACC-002 | `a1_truefix` | 绑定主体-对象 + 角色校验 | `FIXED` / `root_cause` | 根因修复 |
| ACC-003 | `a2_list_only` | 列表按用户过滤 | `UNFIXED` / `list_filtered_not_object` | **列表过滤 ≠ 单对象校验** |

| ACC-005 | `a4_partial` | 详情加了归属校验 | `PARTIAL` / `single_point` | 子资源视图没修 |
| ACC-006 | `a5_vertical` | 水平越权修了 | `PARTIAL` / `vertical_unfixed` | 水平与垂直正交 |
| ACC-007 | `a6_write_silent` | 读接口全加校验 | `UNFIXED` / `silent_write` | **403 但已生效** |

## 三个关键知识点

### 1. 列表过滤 ≠ 单对象校验（ACC-003）

`a2` 把列表查询改成了 `WHERE owner_id = ?`，页面上确实只能看到自己的订单。

但详情接口还是 `SELECT * FROM orders WHERE id = ?`，没有归属校验。

**这是越权里最容易蒙混过关的一种假修复**：演示时点页面永远发现不了，因为前端根本不会去请求别人的 ID。只有直接构造请求才会暴露。

> 知识库判据：`horizontal_effective AND list_filtered` → `list_filtered_not_object`。
> 注意这两个信号**同时为真**才是这个模式——只看 `list_filtered` 会误判成已修复。

### 2. 不可猜测 ≠ 授权（ACC-004）

`a3` 把自增 ID 换成了 UUID。枚举难度确实提高了，但：

- UUID 会出现在分享链接、导出 CSV、前端埋点、日志、第三方回调里
- 本探针就是通过**受害者自己的会话**拿到 UUID 的——真实攻击者同样可以
- 更有意思的是：UUID 让 ID 看起来"随机"，反而降低了审计时的警觉

判据不是"ID 是否可枚举"，而是"**这个主体能不能拿到不属于它的对象**"。

### 3. 403 不等于没生效（ACC-007）

这是整组里最有价值的一条。`a6` 的删除逻辑是：

```python
def delete_order(user, order):
    if order in ORDERS:
        ORDERS.remove(order)          # 先删
    if order["owner_id"] != user["id"]:
        return 403, True              # 再判
    return 200, True
```

越权删除返回 **403**，但数据已经没了。

只按响应码判定的复测会写："已拦截，修复有效。" 而事实是攻击者可以删光别人的订单。

**所以写操作的探针必须回读状态**：删除之后，再用所有者的身份 GET 一次。我们的信号 `silent_write_effective` 就是：

```
delete_status in (401, 403)  AND  after_read_status == 404
```

> 这条也解释了为什么「越权修复的验收」不能只靠接口返回码。
> 读操作可以看状态码，写操作必须看副作用。

## 三维矩阵

越权不是一个维度。完整的阴性证明要覆盖：

| 维度 | 问题 | 本靶场对应 |
|---|---|---|
| 水平 | A 能不能读 B 的数据 | ACC-001/003/004 |
| 垂直 | 普通用户能不能调管理接口 | ACC-006 |
| 子资源 | 同一对象换一个视图还能不能读 | ACC-005 |
| 写操作 | 越权写入是否真的被拦住 | ACC-007 |

少任何一个维度，都可能把一个仍可利用的洞判成已修复。`A07_FIXED` 的五个条件就是这四个维度加基线。

## 和 SQLi / XSS 的对照

| | SQLi | XSS | 越权 |
|---|---|---|---|
| 异常信号 | 响应内容变化 | payload 原样反射 | **没有异常** |
| 判定单位 | 入口 | 上下文 | **（主体, 对象, 动作）三元组** |
| 探针阶段 | 单阶段 | 单阶段 | **两阶段（先当受害者）** |
| 唯一可靠证据 | 数据被读出 | 逃逸序列幸存 | **跨主体访问成功** |
| 典型假修复 | 黑名单 | 上下文错配 | **列表过滤 / UUID / 403 假拦截** |
| 缓解手段 | WAF | CSP | 网关鉴权（仍是缓解） |

同一个 `R01/R02`（不可达 / 基线异常）被三类共用，说明可达性判定确实是类型无关的。

## 已知局限

1. **只有三个账号、单租户**。多租户场景下"租户内校验做了、跨租户没做"是另一个高发模式，未覆盖。
2. **不测参数篡改型提权**。例如请求体里带 `role: admin`、`owner_id` 被前端传入，这类需要按字段做差分测试。
3. **不测令牌伪造**。JWT `alg=none`、弱签名密钥、会话固定都不在范围内。
4. **不测批量接口**。`?ids=1,2,3` 这类入口是常见的遗漏点。
5. **写操作只测了删除**。改状态、改金额、转移归属同样是重灾区。
6. **破坏性探针**。删除会改变状态，所以每次判定前必须 `/reset`；生产环境绝对不能这么测。

## 实施中踩到的坑

**朴素 fallback 崩溃**：加完第三类之后，消融实验直接抛 `KeyError: 'poc_effective'`。

原因是"无知识库"的基线假设所有漏洞类型都有 `poc_effective` 这个信号，而越权的信号里没有它——越权根本没有"PoC 重放"这个概念。

**修复**：fallback 按类型取主信号（SQLi/XSS 用 `poc_effective`，越权用 `horizontal_effective`）。

**反思**：这是抽象泄漏。前两类共用一套信号命名，很容易让人以为那就是通用契约。
第三类一进来就打破了——**「重放 PoC 看通不通」这个心智模型本身不适用于越权**。
这也说明为什么 agent 需要按漏洞类型分派策略，而不是一套探针打天下。
